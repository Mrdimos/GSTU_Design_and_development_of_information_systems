# Лабораторная работа № 3. Событийно-ориентированная подсистема и потоки данных

> Общие правила, таблица вариантов, соглашения по данным/API и шкала оценивания: [`Общие_указания.md`](Общие_указания.md).

**Трудоёмкость:** 2 академических часа.  
**Цель:** Применить EventEmitter и потоки Node.js для регистрации бизнес-событий и обработки файлов без загрузки всего содержимого в память.  
**Основные понятия:** EventEmitter, on/once/emit, обработчики событий, исключения, Readable/Writable/Transform streams, pipeline, backpressure.

### Теоретическая справка

EventEmitter реализует локальную событийную модель: объект публикует событие, а зарегистрированные обработчики реагируют на него. Потоки (streams) позволяют читать, преобразовывать и записывать данные частями. Это снижает потребление памяти и позволяет учитывать backpressure — ситуацию, когда получатель обрабатывает данные медленнее, чем источник их производит. У EventEmitter событие `error` имеет специальное поведение: без подходящего обработчика оно может завершить процесс, поэтому ошибки издателя/слушателей следует явно обрабатывать. Ошибки потоков должны корректно завершать `pipeline` и попадать в понятный обработчик. Для JSONL используют `readline` либо Transform с буфером неполной строки; граница chunk не обязана совпадать с границей строки.

### Индивидуальное задание

Выполните общий алгоритм ниже, а предметную логику возьмите из строки своего варианта в таблице «Индивидуальные требования по вариантам» для этой лабораторной. Не заменяйте индивидуальное требование универсальным примером.

**Обязательный минимум:** все пронумерованные пункты этого раздела, кроме явно перенесённых в «Углублённую часть».

1. Определить минимум три события предметной области: создан объект, изменён статус, выявлена ошибка/нарушение правила.
2. Создать отдельный модуль событийного сервиса на EventEmitter и зарегистрировать обработчики. Вызов каждого слушателя оборачивается в `try/catch` (для async-слушателя обрабатывается отклонение Promise); ошибка одного слушателя записывается в журнал и не прерывает остальные слушатели и основную операцию. Для обработчика, который должен сработать один раз (например, подтверждение), использовать `once`.
3. При выполнении операций из лабораторной № 1 генерировать соответствующие события.
4. Реализовать потоковую обработку текстового или JSONL-файла (по одной записи на строку); подсчитывать записи, фильтровать их или формировать отчёт.
5. Использовать stream.pipeline или async итерацию с корректной обработкой ошибок; не читать большой файл целиком через readFile.
6. Записывать события в журнал с датой, типом события и идентификатором объекта; не записывать пароли, токены и лишние персональные данные.
7. Для JSONL использовать `readline` либо Transform с буфером неполной строки. Не загружать файл целиком: хранить только ограниченное состояние по ключу (например, комнату, сотрудника, аудиторию или оборудование) либо обрабатывать файл, отсортированный по `(ключ, начало)`. В отчёте оценить модель памяти.
8. Проверить пустой файл, некорректную запись и ошибку потока; для слушателя проверить, что ошибка журналируется, но не прерывает остальные слушатели и основную операцию.
