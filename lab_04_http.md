# Лабораторная работа № 4. Низкоуровневый HTTP-сервер средствами Node.js

> Общие правила, таблица вариантов, соглашения по данным/API и шкала оценивания: [`Общие_указания.md`](Общие_указания.md).

**Трудоёмкость:** 2 академических часа.  
**Цель:** Реализовать HTTP-сервер без Express, чтобы понять структуру запросов, маршрутизацию и формирование ответов.  
**Основные понятия:** Модуль http, request/response, методы и статус-коды, заголовки, URL, JSON, чтение тела запроса, ограничения размера тела.

### Теоретическая справка

HTTP использует модель запрос-ответ. Запрос включает метод, путь, заголовки и иногда тело; ответ содержит статус-код, заголовки и тело. Метод описывает действие, а статус сообщает результат. При низкоуровневой реализации приложение самостоятельно разбирает URL и тело запроса, проверяет размер и формат данных и формирует ответ. Для API обычно применяется JSON с корректным Content-Type. Неверные значения полей возвращают `400`; конфликт бизнес-правила, недопустимый переход статуса или занятый ресурс — `409`; неподдерживаемый Content-Type — `415`. Ошибки должны иметь единый формат из «Общих указаний».

### Индивидуальное задание

Выполните общий алгоритм ниже, а предметную логику возьмите из строки своего варианта в таблице «Индивидуальные требования по вариантам» для этой лабораторной. Не заменяйте индивидуальное требование универсальным примером.

**Обязательный минимум:** все пронумерованные пункты этого раздела, кроме явно перенесённых в «Углублённую часть».

1. Создать сервер через http.createServer и вынести обработку маршрутов в отдельную функцию.
2. Реализовать GET для списка и отдельного объекта, POST для создания и PATCH/PUT для изменения статуса либо полей; DELETE — если соответствует предметной области.
3. Разбирать URL через класс URL, проверять метод, параметры и тело запроса.
4. Для JSON-ответов задавать `Content-Type: application/json; charset=utf-8`, для одной HTML-страницы — `text/html; charset=utf-8`; тело запроса читать как поток `Readable`; применять коды `200/201/204/400/404/405/409/413/415/500` по ситуации.
5. Реализовать безопасное чтение тела запроса с лимитом размера, обработкой некорректного JSON и завершением ответа ровно один раз.
6. На этом этапе разрешается хранить данные в памяти; это временное решение, которое позже будет заменено базой данных.
7. Проверить сервер через curl, Postman или аналог: успешные запросы, неизвестный маршрут, неверный JSON, неподдерживаемый метод и неподдерживаемый Content-Type (`415`).
8. Для предметных правил использовать единое отображение ошибок: неверные или отсутствующие поля — `400`; неизвестный объект — `404`; нарушение предметного правила, занятый ресурс, нарушение уникальности и недопустимый переход — `409`.
9. Подключить модули предметной области из ЛР1 и событийный модуль из ЛР3; не копировать их код в HTTP-файл.
