# Лабораторная работа № 5. Диспетчеризация запросов и middleware во фреймворке Express

> Общие правила, таблица вариантов, соглашения по данным/API и шкала оценивания: [`Общие_указания.md`](Общие_указания.md).

**Трудоёмкость:** 2 академических часа.  
**Цель:** Перестроить HTTP-сервер на Express и разделить приложение на маршруты, контроллеры, сервисы и middleware.  
**Основные понятия:** Express, Router, route parameters, query parameters, express.json, middleware pipeline, централизованная обработка ошибок.

### Теоретическая справка

Express строит обработку запроса как цепочку middleware. Каждый middleware может выполнять общую задачу, завершить ответ или передать управление дальше. Router группирует маршруты, controller связывает HTTP с бизнес-логикой, service содержит правила предметной области. В ЛР5 дополнительно создаётся серверная HTML-страница списка сущностей с шаблонизатором (например, EJS, Pug или Handlebars) и автоматическим экранированием вывода; отрицательный XSS-тест должен подтвердить, что ввод пользователя не исполняется как HTML/JavaScript. Ошибка передаётся в централизованный обработчик через `next(err)`; обработчик ошибок Express имеет четыре аргумента `(err, req, res, next)`. Параметры маршрута задают идентификатор ресурса (например, `/items/:id`), а query-параметры используются для фильтрации и пагинации выборки. Централизованный обработчик ошибок обеспечивает единый формат ответа и не допускает раскрытия внутренних трассировок клиенту.

### Индивидуальное задание

Выполните общий алгоритм ниже, а предметную логику возьмите из строки своего варианта в таблице «Индивидуальные требования по вариантам» для этой лабораторной. Не заменяйте индивидуальное требование универсальным примером.

**Обязательный минимум:** все пронумерованные пункты этого раздела, кроме явно перенесённых в «Углублённую часть».

1. Установить Express и создать приложение с отдельными router/controller/service-модулями.
2. Перенести маршруты из лабораторной № 4 на Express, сохранив смысл API и корректные статус-коды.
3. Подключить express.json с разумным лимитом размера тела запроса.
4. Создать минимум два middleware: журналирование запроса и проверка/обработка общего требования (например, correlation ID или проверка обязательного заголовка).
5. Реализовать 404 для неизвестного маршрута и централизованный обработчик ошибок в конце цепочки middleware.
6. Ни в каком режиме не возвращать клиенту stack trace и внутренние подробности ошибок; записывать подробности в серверный журнал с `requestId`. В README зафиксировать major-версию Express и способ передачи ошибок из async-обработчиков.
7. Создать HTML-страницу списка предметных сущностей через EJS, Pug или Handlebars; использовать экранированный вывод и проверить отрицательный XSS-сценарий.
8. Проверить порядок middleware, валидацию параметров, ответ `400` при неверном запросе, `413` при превышении лимита тела и одинаковый формат ошибок.
