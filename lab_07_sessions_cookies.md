# Лабораторная работа № 7. Управление сессиями и безопасностью cookies

> Общие правила, таблица вариантов, соглашения по данным/API и шкала оценивания: [`Общие_указания.md`](Общие_указания.md).

**Трудоёмкость:** 2 академических часа.  
**Цель:** Реализовать состояние пользовательского сеанса с помощью cookies и серверных сессий.  
**Основные понятия:** Cookie, Set-Cookie, HttpOnly, Secure, SameSite, срок действия, express-session, session ID, хранение сессий и секрет подписи.

### Теоретическая справка

Cookie — небольшое значение, которое браузер отправляет серверу в последующих запросах. Серверная сессия хранит состояние на стороне сервера, а клиент обычно передаёт идентификатор сессии через cookie. `HttpOnly` запрещает чтение cookie из JavaScript, `Secure` требует HTTPS, `SameSite` ограничивает часть межсайтовой отправки. Cookie с идентификатором сессии обычно подписана, чтобы обнаружить подмену; подпись не шифрует значение. `req.session.regenerate()` после входа снижает риск session fixation. CSRF возникает, когда браузер автоматически прикладывает cookie к нежелательному запросу; защита зависит от схемы аутентификации и атрибутов cookie.

### Индивидуальное задание

Выполните общий алгоритм ниже, а предметную логику возьмите из строки своего варианта в таблице «Индивидуальные требования по вариантам» для этой лабораторной. Не заменяйте индивидуальное требование универсальным примером.

**Обязательный минимум:** все пронумерованные пункты этого раздела, кроме явно перенесённых в «Углублённую часть».

1. Реализовать демонстрационный вход по логину для seed-пользователей из ЛР6; пароль на этом этапе не проверяется (хеширование и проверка — ЛР8). Маршрут доступен только при `DEMO_AUTH=1` и не включается по умолчанию; при `DEMO_AUTH` отсутствующей или отличной от `1` маршрут не регистрируется либо возвращает `404`.
2. Настроить `express-session` с секретом из переменной окружения и безопасными параметрами cookie (`HttpOnly`, `SameSite`, срок действия; `Secure` согласно HTTP/HTTPS окружению). После успешного demo-входа вызывать `req.session.regenerate()`.
3. Реализовать маршрут просмотра текущего сеанса и выход с уничтожением сессии и очисткой cookie.
4. Проверить сохранение сессии между запросами одного клиента и изоляцию от второго клиента.
5. Не хранить в cookie пароль, JWT или доверенную роль; в сессии сохранять только минимальный идентификатор пользователя и необходимое служебное состояние.
6. Cookie с идентификатором сессии должна быть подписана; проверить подмену cookie и описать, что подпись обнаруживает изменение, но не шифрует содержимое.
7. Подключить Redis как хранилище сессий через `REDIS_URL`. При использовании общего Redis кафедры у каждого студента должна быть отдельная учётная запись/ACL с правами только на собственный префикс ключей; использовать `REDIS_URL` с логином и паролем из `.env`, не передавать учётные данные в отчётах. Префикс сессий должен быть уникальным, например `sess:<номер-студента-или-группы>:`. Общий Redis должен требовать аутентификацию. Если общего сервера нет, использовать локальный `docker-compose.yml` или Redis в WSL2. `MemoryStore` допускается только при недоступности Redis и требует письменного обоснования; `MemoryStore` не является production-хранилищем.
8. В отчёте описать CSRF-риск и меры защиты для cookie-аутентифицированных изменяющих запросов. Реализация CSRF-токена остаётся углублённой частью.
