# Лабораторная работа № 8. Аутентификация, JWT и ролевая авторизация

> Общие правила, таблица вариантов, соглашения по данным/API и шкала оценивания: [`Общие_указания.md`](Общие_указания.md).

**Трудоёмкость:** 4 академических часа.  
**Цель:** Реализовать безопасную регистрацию/вход и проверку прав пользователей для защищённых маршрутов.  
**Основные понятия:** bcrypt, аутентификация и авторизация, JWT, access/refresh token, middleware, RBAC, принцип наименьших привилегий.

### Теоретическая справка

Аутентификация отвечает на вопрос «кто пользователь?», авторизация — «что ему разрешено?». `bcrypt` использует соль, которая делает одинаковые пароли разными хешами, и параметр стоимости (`cost`), влияющий на вычислительную цену проверки; стоимость нужно выбирать и фиксировать осознанно. JWT содержит claims и подпись; подпись проверяет целостность, но не скрывает содержимое. Middleware проверяет алгоритм подписи, срок действия, права и владение объектом. Refresh-токен используется для получения нового короткоживущего access-токена и должен иметь отдельный срок жизни и механизм отзыва.

### Индивидуальное задание

Выполните общий алгоритм ниже, а предметную логику возьмите из строки своего варианта в таблице «Индивидуальные требования по вариантам» для этой лабораторной. Не заменяйте индивидуальное требование универсальным примером.

**Обязательный минимум:** все пронумерованные пункты этого раздела, кроме явно перенесённых в «Углублённую часть».

1. Расширить таблицу `users` из ЛР6: сохранить уникальные `login`/`email` и `role`, добавить `password_hash` миграцией `lab_08_users_password_migration.sql`. Не создавать вторую таблицу пользователей.
2. Реализовать регистрацию/seed-обновление с валидацией и хешированием пароля через `bcrypt`; пояснить соль и выбранную стоимость (`cost`). Публичная регистрация назначает только минимальную роль и отклоняет поле `role` из тела запроса; изменение роли доступно только системной роли `admin`. Во всех вариантах существует системная роль `admin`; первый администратор создаётся seed-скриптом, пароль берётся из переменной окружения, а не хранится в файле. Пароль в открытом виде не хранить.
3. Реализовать вход и короткоживущий JWT access-токен с явным разрешённым алгоритмом подписи, `sub`, `iat`, `exp`; ключ хранить в окружении. При неверном логине и неверном пароле возвращать одинаковый `401`; ограничить частоту попыток входа и протестировать срабатывание лимита.
4. Создать middleware проверки токена и middleware проверки роли/разрешения; актуальные права на объект проверять по данным приложения, а не только по данным клиента.
5. Защитить минимум три операции: доступную любому аутентифицированному пользователю, доступную владельцу/исполнителю объекта и административную. Для чужого объекта выбрать и обосновать `403` или маскирующий `404`.
6. Добавить миграцию таблицы `refresh_tokens` (`id`, `user_id`, `token_hash`, `expires_at`, `revoked_at`) с внешним ключом на `users`; использовать её для хранения хеша, ротации и отзыва refresh-токенов. Возвращать refresh-токен в теле ответа для учебного API, хранить клиентом только в памяти демонстрационного клиента (не в `localStorage`); задать срок действия и отзыв при выходе. Не выдавать долгоживущий access-токен.
7. Проверить отсутствие токена, неверную подпись, истёкший access-токен, неверную роль и попытку изменить чужой объект.
8. Удалить или отключить demo-вход из ЛР7: итоговый проект выполняет вход только по логину и паролю. Негативный тест должен подтвердить, что вход без пароля и demo-маршрут возвращают `401`/`404` и не создают аутентифицированную сессию.
9. Сопоставить JWT с сессиями из ЛР7: это разные механизмы, их не требуется дублировать для одного и того же маршрута без архитектурного обоснования.
