# Лабораторная работа № 9. REST API, валидация и документирование веб-служб

> Общие правила, таблица вариантов, соглашения по данным/API и шкала оценивания: [`Общие_указания.md`](Общие_указания.md).

**Трудоёмкость:** 4 академических часа.  
**Цель:** Привести интерфейс приложения к согласованному REST-подходу, добавить валидацию и документацию API.  
**Основные понятия:** Ресурсы и URI, GET/POST/PUT/PATCH/DELETE, идемпотентность, коды HTTP, Joi/Yup или аналог, пагинация, фильтрация, OpenAPI.

### Теоретическая справка

REST — набор архитектурных ограничений, в том числе ресурсная модель и единообразный интерфейс. Методы имеют семантику: GET читает, POST обычно создаёт/запускает обработку, PUT заменяет ресурс, PATCH изменяет часть, DELETE удаляет. Идемпотентность означает, что повтор одинакового запроса имеет тот же конечный эффект. Серверная валидация обязательна даже при проверках на клиенте. Пагинация ограничивает размер ответа, фильтрация выбирает подмножество данных, а OpenAPI описывает контракт и схемы API. `403` означает отказ в доступе, `404` — отсутствие ресурса; для чужих объектов допустимо согласованное `404`, чтобы не раскрывать их существование. `422` можно использовать для синтаксически корректного, но семантически недопустимого содержимого, если политика единообразна. Документация фиксирует контракт API.

### Индивидуальное задание

Выполните общий алгоритм ниже, а предметную логику возьмите из строки своего варианта в таблице «Индивидуальные требования по вариантам» для этой лабораторной. Не заменяйте индивидуальное требование универсальным примером.

**Обязательный минимум:** все пронумерованные пункты этого раздела, кроме явно перенесённых в «Углублённую часть».

1. Проверить и унифицировать имена ресурсов и маршрутов: существительные во множественном числе, вложенность только при необходимости. Если ресурс принадлежит родительскому объекту, путь имеет вид `/<родитель>/:id/<ресурс>`; не использовать отдельные `/versions`, `/expenses`, `/bookings` без родителя.
2. Определить корректные методы и коды ответа для создания, чтения, изменения и удаления. Зафиксировать политику `400`/`422` для ошибок входных данных и `403`/`404` для доступа к чужому объекту; конфликт состояния возвращает `409`.
3. Добавить схему валидации тела, параметров пути и query-параметров на Joi или Yup (выбранную библиотеку и её версию зафиксировать в README); отклонять неизвестные/недопустимые поля согласно выбранной политике.
4. Реализовать фильтрацию и пагинацию списка; установить разумные ограничения page/limit.
5. Обеспечить согласованный формат ошибки с кодом/сообщением без утечки внутренностей.
6. Подготовить машиночитаемую спецификацию OpenAPI для основных маршрутов, схем запросов/ответов, ошибок и требований аутентификации. README может содержать пояснения и инструкции запуска, но не заменяет OpenAPI.
7. Проверить API в Postman/curl: успешные запросы, невалидные данные, отсутствие доступа, неизвестный ресурс и повторный запрос.
