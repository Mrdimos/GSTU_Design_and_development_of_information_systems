# Лабораторная работа № 10. Двусторонний обмен данными в реальном времени с Socket.IO

> Общие правила, таблица вариантов, соглашения по данным/API и шкала оценивания: [`Общие_указания.md`](Общие_указания.md).

**Трудоёмкость:** 4 академических часа.  
**Цель:** Добавить в корпоративную систему событийные уведомления в реальном времени с контролем доступа к каналам.  
**Основные понятия:** WebSocket и HTTP upgrade, Socket.IO, connection/disconnect, emit/on, rooms, broadcast, namespaces, повторное подключение.

### Теоретическая справка

WebSocket предоставляет постоянный двунаправленный канал связи. Socket.IO добавляет собственный протокол событий, комнаты, повторное подключение и другие удобства, поэтому он не тождествен нативному WebSocket. Комнаты позволяют отправлять сообщения подмножеству клиентов. Идентификатор комнаты, переданный клиентом, не является доказательством права доступа: сервер обязан проверять личность и полномочия. Обязательны пользовательский namespace и отдельный защищённый namespace `/admin`, например с событиями `service:health` и `connections:count`, доступными только администратору. Для горизонтального масштабирования может потребоваться адаптер/брокер событий.

### Индивидуальное задание

Выполните общий алгоритм ниже, а предметную логику возьмите из строки своего варианта в таблице «Индивидуальные требования по вариантам» для этой лабораторной. Не заменяйте индивидуальное требование универсальным примером.

**Обязательный минимум:** все пронумерованные пункты этого раздела, кроме явно перенесённых в «Углублённую часть».

1. Подключить Socket.IO к существующему HTTP-серверу Express; не запускать второй независимый сервер без причины.
2. Определить минимум два события: новое/изменённое состояние предметного объекта и подтверждение/прочтение уведомления.
3. Аутентификацию сокета выполнять в `io.use` тем же механизмом, что защищает REST (выбор и обоснование записать в README по итогам сравнения ЛР8). Если используется cookie-сессия, проверка заголовка `Origin` при подключении обязательна. Право вступить в комнату проверять по данным БД, используя членство из ЛР6, а не payload клиента. Не доверять произвольному room ID от клиента.
4. Использовать rooms для рассылки только заинтересованным пользователям/подразделениям; не отправлять все события всем клиентам.
5. Генерировать уведомление после успешного изменения данных, а не до сохранения; учитывать ошибки БД. Публиковать уведомление через событийный модуль ЛР3 после успешного сохранения.
6. Реализовать обработку disconnect и ошибочного payload; валидировать входящие сообщения. Payload уведомления содержит тип изменения и идентификаторы; полные записи с персональными данными по сокету не передаются. При повторном подключении заново выполнять аутентификацию и проверку членства до повторного вступления клиента в комнаты.
7. Создать два namespace: основной пользовательский (например, `/app`) и защищённый `/admin` с событиями `service:health` и `connections:count`; доступ к `/admin` получает только системная роль `admin`. Роли `app_admin` (вариант 14) и `infrastructure_admin` (вариант 20) администрируют только свои предметные области, если им отдельно не выдана системная роль `admin`.
8. Продемонстрировать два клиента и показать, что каждый получает только разрешённые уведомления. В отчёте указать ограничения локального single-process решения и возможную роль адаптера/брокера при масштабировании.

### Углублённая часть

В углублённой части добавить повторную проверку прав при истечении access-токена или отзыве членства уже после установления соединения и ограничение размера входящего payload. Проверка `Origin` обязательна в основном задании, если используется cookie-аутентификация.
