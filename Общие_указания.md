# Общие указания к практикуму «Проектирование и разработка корпоративных информационных систем»

Специальность 6-05-0611-01 «Информационные системы и технологии», 4-й курс.

## 1. Общая концепция

Все лабораторные выполняются как этапы **одной корпоративной информационной системы**. Студент получает один вариант из раздела 2 и использует его во всех десяти работах. Нельзя каждый раз начинать новый проект: результаты предыдущих лабораторных развиваются и переиспользуются. В лабораторной № 4 создаётся сервер на модуле `http`, а в № 5 он переносится на Express. В № 6 временное хранение в памяти заменяется базой данных. В № 7 демонстрируется сессионный подход, а в № 8 добавляется JWT-аутентификация как отдельный механизм для защищённых API-маршрутов; в отчёте нужно сравнить подходы и не дублировать их без архитектурного обоснования.

### Базовые технические соглашения

- Зафиксировать используемую major-версию Node.js, Express и основных библиотек в README; выбрать один модульный формат (рекомендуется ES Modules). Версию Node.js и npm указывать в инструкции запуска. Lockfile хранить в репозитории и использовать `npm ci` для воспроизводимой установки.
- Основная реализация постоянного хранения выполняется на SQL-БД; для снижения сложности рекомендуется SQLite с библиотекой `better-sqlite3` (возможны нативные бинарные зависимости и проблемы установки на некоторых конфигурациях Windows — проверить до занятия). По согласованию с преподавателем допускается PostgreSQL. Документная СУБД рассматривается в сравнительном разделе отчёта, но не заменяет основную SQL-реализацию. Это учебное сравнение, а не практическая интеграция второй СУБД.
- Применять параметризованные SQL-запросы, серверную проверку входных данных и централизованную обработку ошибок. Единый формат ошибки: `{ "error": { "code": "ERROR_CODE", "message": "Краткое сообщение", "requestId": "идентификатор запроса" } }`. Стек вызовов и внутренние подробности не возвращать клиенту ни в одном режиме; писать их в серверный журнал вместе с `requestId`.
- Конфигурацию и секреты хранить в переменных окружения; добавить `.env.example` только с фиктивными значениями. В `.gitignore` включить `.env`, `node_modules/` и файл/файлы локальной БД. Настоящий `.env` не должен попадать в историю Git ни в одном коммите; если секрет попал в историю, удалить его недостаточно — секрет необходимо заменить, а историю очистить по согласованной процедуре.
- Не использовать реальные персональные данные, настоящие пароли, рабочие ключи или корпоративные данные. Использовать синтетические тестовые наборы.
- Графический интерфейс не требуется, кроме обязательной серверной HTML-страницы с шаблонизатором в ЛР5. HTTP можно проверять через `curl` или бесплатный клиент без обязательной учётной записи; Socket.IO — минимальным клиентом на `socket.io-client` и/или бесплатным инструментом, выбранным студентом. Автоматические тесты выполняются встроенным `node:test` либо согласованной бесплатной библиотекой; конкретные версии и команды фиксируются в README.
- Для каждой лабораторной сохранять состояние проекта в системе контроля версий или в отдельной копии/теге, чтобы можно было показать этапы разработки.

### Единые правила данных и API

- Даты и время передавать и хранить в UTC в формате ISO 8601. Для интервалов использовать полуоткрытую модель `[start, end)`: начало включается, конец не включается.
- Денежные значения хранить целым числом в минимальных денежных единицах (например, копейках) либо типом `DECIMAL/NUMERIC`; не использовать двоичный `float` для денежных расчётов.
- Для HTTP API использовать единый формат ошибки, указанный выше. `requestId` должен возвращаться клиенту и присутствовать в серверном журнале.
- Согласованное отображение ошибок: синтаксически некорректный JSON и неверные/отсутствующие обязательные параметры — `400`; отсутствие/ошибка аутентификации — `401`; аутентифицированному пользователю запрещено действие — `403` (или обоснованный маскирующий `404` для чужого объекта); объект не найден — `404`; конфликт бизнес-состояния, занятый ресурс, нарушение уникальности или недопустимый переход статуса — `409`; неподдерживаемый Content-Type — `415`; слишком большое тело запроса — `413`; внутренняя ошибка — `500` без внутренних деталей в ответе. В ЛР9 допустимо выбрать `422` для синтаксически корректного тела, которое не проходит семантическую схему валидации; выбранную политику необходимо одинаково применять и описать в OpenAPI.
- Загрузка `.env` выполняется одним явно указанным способом: встроенный `node --env-file` или пакет `dotenv`; выбранный способ и требуемая версия Node.js указываются в README.
- Для вариантов с уведомлениями о приближении/просрочке срока (1, 4, 7, 13, 15, 16, 19, 24, 30) явно выбрать механизм: периодическая проверка по расписанию либо проверка при чтении/изменении объекта; указать компромисс и покрыть тестом границу срока.
- Варианты должны проверять не только успешные запросы, но и минимум два негативных сценария. Для правил лимита, уникальности и непересечения требуется защита на уровне БД (`CHECK`, `UNIQUE`/частичный индекс, условный `UPDATE` либо проверка и вставка в одной транзакции). Тест двух параллельных запросов относится к углублённой части ЛР6, если он не назначен преподавателем отдельно.

### Безопасность и блокирующие дефекты

Лабораторные № 6–10 оцениваются с учётом безопасности. Если обнаружен пароль в открытом виде в постоянном хранилище, действующий секрет в репозитории/истории Git или отсутствие проверки владения объектом/членства в комнате в ЛР8–ЛР10, итоговая оценка соответствующей лабораторной **не может превышать 4 из 10 баллов** до устранения дефекта и повторной проверки. Если студент устраняет дефект до защиты, ограничение снимается. Преподаватель может применить более строгие локальные правила.

### Учёт времени и заочное отделение

Учебная нагрузка дневного отделения составляет 26 академических часов: ЛР1–ЛР7 — по 2 часа, ЛР8–ЛР10 — по 4 часа. Заочное отделение — 6 академических часов. Часы не перераспределяются. В каждой работе обязательный минимум входит в оценку, углублённая часть выполняется по желанию или по заданию преподавателя. Для заочного отделения обязательный минимум выполняется самостоятельно до занятия; на занятии проводится защита и проверка результатов. Минимум: рабочий проект, ключевой сценарий индивидуального варианта, минимум два негативных теста и краткий отчёт.

### Взаимное ревью кода

В ЛР9 проводится короткое парное code review: студент проверяет у партнёра структуру маршрутов, валидацию, обработку ошибок, секреты и проверку доступа, а автор исправляет минимум одно подтверждённое замечание либо письменно объясняет, почему оно неприменимо. В отчёте фиксируются замечание, решение и результат повторной проверки.

### Сквозная архитектура к концу цикла

`HTTP-клиент → Express Router → middleware → controller → service/business rules → repository → database`; отдельные модули обеспечивают CLI, события/журналирование и Socket.IO. Сокет-события отправляются только после успешного изменения данных и только тем клиентам, которым разрешён доступ.

### Согласованные сущности, статусы, роли и маршруты

#### Определения предметных сущностей

- `responsibility_zone` (вариант 20, зона ответственности) — именованная группа серверов/сервисов с назначенным ответственным инженером или командой, порогами метрик и списком получателей инцидентных уведомлений.
- `workshop_section` (варианты 27–28, производственный участок) — физическая производственная зона/линия, к которой привязываются изделия, дефекты или производственные заказы.
- `department` (варианты 5, 23–24, подразделение) — организационная единица предприятия; в варианте 24 она отвечает за лицензии и назначенные устройства, в варианте 23 участвует в согласовании закупки ПО.
- Для варианта 17 `work_center` — рабочий центр/производственный ресурс; `operator` — исполнитель операции, `master` — производственный мастер/руководитель участка. Это разные роли.
- Для варианта 12 `employee` — базовая учётная запись, а `teacher` — предметная роль сотрудника, которому разрешено управлять собственными занятиями.
- Для варианта 14 предметные разрешения на конкретные корпоративные ресурсы хранятся отдельно от системного RBAC: системная роль отвечает за доступ к функциям приложения, предметное разрешение — за доступ к конкретному ресурсу.
- Для варианта 27 обязателен справочник `defect_types` как минимум со значениями `material`, `dimensional`, `surface`, `assembly`, `electrical`, `packaging`. В записи дефекта хранится ссылка на справочник (`defect_type_id` или `code`), а не произвольный текст.

#### Допустимые переходы статусов

| Вариант | Объект | Допустимые переходы | Ограничение |
|---:|---|---|---|
| 1 | `it_request` | `new → assigned → in_progress → resolved → closed` | `resolved → in_progress` разрешён при повторном открытии с записью причины; остальные переходы проверяются явно. |
| 6 | `document` | `draft → pending_approval → approved` или `rejected`; `rejected → draft` | Утверждать документ может согласующий; автор не утверждает собственный документ, если требуется независимое согласование. |

Роль не принимается из тела запроса как доверенное значение. `users.role` — системная роль (`admin`) либо базовая роль варианта; `user_roles(user_id, role)` хранит дополнительные предметные роли там, где это требуется (в частности, варианты 12 и 14). Публичная регистрация назначает только самую слабую роль, предусмотренную строкой соответствующего варианта в ЛР8 (например, `viewer`, `employee`, `requester`, `customer`, `learner` или `member`); выбранную базовую роль для публичной регистрации обязательно фиксируют в README студенческого проекта. `admin` управляет пользователями, системными ролями и namespace `/admin`; предметные роли `*_admin` управляют только данными своей предметной области. Для вариантов 14 и 20 роли `app_admin` и `infrastructure_admin` являются администраторами своих областей, а не заменой системной роли `admin`.

#### Принцип именования REST-ресурсов

Имена ресурсов — естественные существительные во множественном числе; одинаковые пути в разных вариантах допустимы, поскольку каждый студент выполняет только один вариант. Вложенность используйте лишь для ресурса, действительно принадлежащего родительскому объекту. Примеры: вариант 8 — `/api/rooms` и `/api/rooms/:roomId/bookings`; вариант 9 — `/api/vehicles` и `/api/trips`; вариант 12 — `/api/classrooms` и `/api/lessons`; вариант 20 — `/api/servers/:serverId/metrics` и `/api/incidents`; вариант 22 — `/api/labs`, `/api/computers` и `/api/support-requests`.

Каждому студенту назначается один номер. Этот номер используется во всех десяти лабораторных. Если студентов меньше 30, используются только назначенные номера. Для группы больше 30 применяется правило дополнительных ограничений из подраздела «Правило закрепления варианта».
